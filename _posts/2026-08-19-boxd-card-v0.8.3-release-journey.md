## Three releases in twenty-one hours

I sat down on Sunday to have Claude run a security audit on [Boxd Card](https://boxd-card.com).
By Wednesday evening Boxd Card had shipped v0.8.1, v0.8.2 and v0.8.3.

Claude drew this Gantt chart on Sunday as a forecast, before any of it shipped. The dashed bar near
the bottom is what it predicted for the Chrome Web Store; the diamond nine days to its
left is where the extension actually went live. Everything else below is why.

The audit itself went the way audits go. The headline finding was real and worth the
weekend: Grafana Faro's automatic instrumentation was capturing Letterboxd usernames and
film slugs in five separate places, while the privacy policy for Boxd Card promised
it wasn't. That fix shipped Monday morning, and Claude confirmed it in Loki — 200-plus
lines ingested afterwards, none of them carrying a URL or a slug.

## Some card types have shipped but haven't been properly tested

Before publishing 0.8.2 I did the manual checks I'd been putting off, generated a
Milestones card, and got this: the Letterboxd logo, my name, the heading "Milestones",
the footer — and between them, nothing at all. An empty band where six film posters
should be.

An empty card is a strange bug. It isn't a crash, so nothing is logged. It isn't wrong
data, so nothing looks suspicious. It's a card that renders perfectly and says nothing,
which is the failure mode most likely to survive a casual look.

The cause was two lines:

```js
const container = document.querySelector('.milestone-group.-diaryevents')
if (!container) return { diaryMilestones: [] }
```

When the selector missed, the scraper returned an object. Not `null`, not an error — an
object, with an empty array inside it. Downstream, the popup asked the only question it
knew how to ask:

```js
// condensed; the real guard tests six payload fields, this being one
if (!filmData.milestonesData) throw new Error('No stats data found on this page.')
```

An empty object is truthy. The guard passed. The renderer drew a header, drew a footer,
drew nothing in between, and reported success.

## Why the selector missed

Letterboxd publishes milestones on your Year in Review page, `/user/year/2026/`. It does
not publish them on your all-time stats page, `/user/stats/`. Both pages are built from
the same stylesheet, both are Pro-only, both matched the same URL pattern in my
extension — so it offered Milestones on a page where the markup has never existed.

Claude checked the live DOM on both, and the answer was blunt:

| Category | `/stats/` | `/year/2026/` |
| --- | --- | --- |
| Summary, genres, countries, languages | yes | yes |
| Most Watched, Rated Higher Than Average | yes | yes |
| Films by Week | **no** | yes |
| Ratings & Breakdown | **no** | yes |
| Milestones | **no** | yes |

Three categories were dead on the all-time page, not one. I had only noticed Milestones
because it was the one I happened to test.

One category survived, and the reason is instructive: Most Watched was the only scraper
that ever asked which page it was on. It had a branch — year page reads one bit of
markup, all-time reads another. Every other category assumed the two pages were
interchangeable. The one that checked, worked.

## Each fix revealed the next

Fixing the page mismatch made the card render. Making the card render exposed a second
bug: the posters were capped at 160 pixels in a single row, while the card's height came
from whichever layout you'd picked. On a 3:4 card that left about 60% of the canvas empty.

That bug had been there since v0.8.0.

And the working card finally exercised a *third* fix, one I'd shipped in 0.8.2 without
ever seeing it work. Letterboxd had moved film IDs out of a `data-film-id` attribute and
into a JSON blob, which collapsed the poster lookup so every milestone slot showed the
same artwork. The correction went out with its tests passing and no way to confirm it,
because the card was empty before the fix could be reached. Regenerating Milestones after
the layout work was the first time I actually saw six different posters.

Three defects, stacked. Each one hiding the next.

## The fix that matters isn't the selector

I could have updated the selector and moved on. That would have fixed Wednesday's bug and
guaranteed Friday's, because this codebase has *already* been bitten by Letterboxd
renaming markup — that's exactly what `data-film-id` was.

The durable fix is the other one: a scrape that finds nothing now fails loudly instead of
returning an empty shape for the renderer to draw. An empty card is never a correct
outcome, so there's no false-positive cost to treating it as an error. That single change
converts every future DOM change from a silent blank into a visible message.

It also would have caught all three broken categories, including the two nobody had
thought to test. The selector fix addresses one incident; the guard addresses the class.

Posters now size themselves to the space available and wrap when that makes them bigger —
on a 3:4 card, 146-pixel posters in one row became 280-pixel posters in a 3×2 grid.
Getting the wrapping right took two attempts: Claude's first tie-breaking rule fixed
two-entry cards and quietly regressed the tall story format from 94% fill to 62%. That
only surfaced because it printed the solver's output across all six layouts before
trusting it, rather than eyeballing the one case we started from.

## Then the release itself went wrong

Boxd Card has a two-branch setup: `main` is the development gate, `release` is the release
trigger. Pushing to `release` runs a workflow that builds, tests, packages the extension
zip, creates the tag, and publishes a GitHub Release. Claude merged 0.8.3 to `main`, called
it done, and created the tag by hand.

I asked why the release workflow hadn't fired. That question is the only reason the tag
ended up on the right commit.

The hand-made tag was worse than useless. The workflow skips tag creation when the tag
already exists, so the release would have attached its zip to a commit on the wrong branch.
And `Version Check` — the job that exists to catch exactly this — would have *passed*,
because it allows an existing tag that's reachable from HEAD, reading that as "you're only
syncing content that already shipped". A tag on the tip of `main` satisfies that condition
perfectly. The guard waves through the one case it looks like it is guarding.

The part I hadn't expected: Claude already had this branch topology written down in its own
notes, correctly, and didn't read them. Having the right answer on file turns out to be a
different thing from consulting it.

## What the plan got wrong

Claude had drawn a rollout plan on Sunday with three tracks and an eleven-day estimate for the
Chrome Web Store. The review cleared in hours. Being pessimistic about a queue you don't
control is still the right instinct — under-estimating it would have stranded a privacy
fix behind Google — but the estimate was wrong, and future ones should be pared down:
changes between releases are incremental, and review is correspondingly lighter.

The Faro API key needed `sourcemaps:write`, not the `frontend-observability:write` Claude
had on file and had me request repeatedly while collecting 401s. Diagnosing it was slowed
by a probe that lied: the API authenticates before parsing the request body but authorises
scope *after*, so an empty request returns a body-parsing error without ever checking
scope — which reads exactly like success.

And the Worker's rate limiting was wired two ways, neither working. The first used a
config form that deploys cleanly, prints reassuring output, and is silently inert. The
corrected version counts per-isolate, so 695 requests against a single key produced zero
denials. It's a brake, not a cap. A real limit needs a dashboard rule, which is now in place
for `api.boxd-card.com`.
